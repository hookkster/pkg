# pkg

Общий код сервисов hookster: структурированное логирование, gRPC-интерцепторы, работа с JWT.

## Подключение

```bash
go get github.com/hookkster/pkg@latest
```

## Состав

| Пакет | Назначение |
|---|---|
| `logger/sl` | Конструктор `*slog.Logger`, trace_id в контексте, маскирование PII |
| `logger/handlers/slogpretty` | Цветной хендлер для локальной разработки |
| `interceptors` | gRPC-интерцепторы: логирование, recovery, проброс trace_id |
| `jwtmanager` | Выпуск и проверка JWT (RS256), разделение access/refresh |

## logger/sl

### Создание

```go
log := sl.NewLogger(sl.Config{
    Env:     cfg.Env,   // local | dev | prod
    Service: "auth-service",
    Version: version,   // git-тег или короткий SHA, обычно из ldflags
})
```

`Env: "local"` даёт цветной вывод для человека. **Любое другое значение — JSON.** Сделано намеренно: сервис, тихо пишущий ANSI-последовательности в лог-шиппер, обнаруживается куда позже, чем сервис, пишущий JSON на ноутбуке разработчика.

`Service` и `Version` — константа и переменная уровня пакета в `main`, не поле конфига: они не меняются между окружениями, а меняются с каждой сборкой или никогда.

`Output` переопределяет `os.Stdout`, нужен только в тестах.

### trace_id

Идентификатор запроса живёт в контексте и подставляется в записи автоматически:

```go
ctx = sl.WithTraceID(ctx, sl.NewTraceID())
```

`NewTraceID` возвращает 32 hex-символа — формат W3C trace-id, тот же, что у OpenTelemetry.

**Работает только с Context-вариантами методов:**

```go
log.InfoContext(ctx, "user created")   // trace_id попадёт в запись
log.Info("user created")               // trace_id НЕ попадёт
```

Обычный `Info` передаёт slog фоновый контекст, из которого нечего доставать — это ограничение `log/slog`, обойти нельзя. В сервисном коде используются только `InfoContext` / `WarnContext` / `ErrorContext` / `DebugContext`.

В фоновой горутине (например, асинхронное создание профиля после регистрации) trace_id из родительского контекста не наследуется — его нужно достать до запуска горутины и положить в новый контекст явно:

```go
traceID := sl.TraceID(ctx)
go func(traceID string) {
    bgCtx := sl.WithTraceID(context.Background(), traceID)
    // ...
}(traceID)
```

### Маскирование

```go
log.With(sl.Identifier(phone))       // 89*******21
log.With(sl.Masked("email", email))  // i****@mail.ru
```

Централизованное хранилище логов хранит записи неделями и читается всеми, у кого есть доступ к дашборду — телефон или email в открытом виде там персональные данные, которые никто не собирался хранить в незащищённом виде. Маска оставляет достаточно, чтобы узнать значение, которое уже знаешь, но не хватает, чтобы прочитать чужое.

### Прочее

`sl.Err(err)` — атрибут с текстом ошибки, безопасен при `nil`.

`sl.Into(ctx, log)` / `sl.From(ctx)` — положить и достать логгер из контекста, когда прокидывать его через конструкторы неудобно.

## interceptors

### Серверные

```go
grpcServer := grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        interceptors.UnaryLogging(log),
        interceptors.UnaryRecovery(log),
    ),
)
```

**Порядок важен.** `UnaryLogging` кладёт trace_id в контекст и должен быть внешним — иначе запись о панике останется без идентификатора запроса. Паника не возвращается, а разматывает стек: окажись recovery снаружи, logging не успеет дописать строку о завершении вызова, и в логах будет паника без метода, длительности и кода ответа. Плата за такой порядок — паника внутри самого `UnaryLogging` не перехватывается; кода, обращающегося к внешним системам, там нет, риск считается приемлемым.

**UnaryLogging** пишет одну запись на завершённый вызов: метод, длительность, код gRPC, ошибку (если есть). Уровень определяется кодом ответа, а не фактом ошибки:

| Уровень | Коды |
|---|---|
| Info | `OK` |
| Error | `Internal`, `Unknown`, `DeadlineExceeded`, `Unavailable`, `DataLoss` |
| Warn | всё остальное |

Разделение нужно для алертинга: неверный OTP-код — штатная работа системы, и если он пишется как Error, алерт на error rate звенит на каждой опечатке пользователя и через неделю отключается навсегда — вместе с сигналом о настоящей аварии.

trace_id берётся из входящих метаданных, если он там есть, иначе генерируется новый.

**UnaryRecovery** превращает панику в `codes.Internal`, пишет значение паники и стек вызовов в лог. Клиенту уходит `"internal error"` без подробностей — значение паники может нести путь, ключ или фрагмент запроса.

### Клиентский

```go
conn, err := grpc.NewClient(addr,
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithUnaryInterceptor(interceptors.UnaryClientTraceID()),
)
```

Копирует trace_id из контекста в исходящие метаданные. Без него трассировка обрывается на первой границе между сервисами: вызывающий пишет логи под одним идентификатором, вызываемый генерирует себе новый, и склеить их невозможно.

Ключ метаданных — `interceptors.TraceIDKey` (`x-trace-id`), общий для отправителя и получателя.

## jwtmanager

RSA-подписанные токены (RS256) с явным разделением access и refresh.

### Почему нужен тип токена

Access и refresh отличаются не только сроком жизни, но и частотой использования: access ездит в каждом запросе и потому короткий, refresh предъявляется раз в 15 минут на одном эндпоинте и потому может жить дольше. Без claim с типом refresh-токен проходит любую проверку access-токена — то есть токен на 30 дней даёт 30 дней доступа к защищённым методам, а не только право обновить сессию.

### Создание

```go
manager, err := jwtmanager.NewManager(privatePEM, publicPEM)
```

Оба ключа необязательны — передаётся то, что сервису действительно нужно. Auth-service подписывает токены и получает приватный ключ; сервисам, которые только проверяют чужие подписи, достаточно публичного. Вызов `Generate` без приватного ключа или `Verify` без публичного вернёт ошибку, а не панику.

Ключи в формате PEM. Держите их вне репозитория — приватный ключ подписывает токены всей системы.

### Выпуск

```go
token, err := manager.Generate(userID, role, jwtmanager.TokenAccess, ttl)
```

`TokenType` — `jwtmanager.TokenAccess` или `jwtmanager.TokenRefresh`, попадает в claims как `typ`. В токен также идут `user_id`, `role`, `iat`, `exp`.

### Проверка

```go
info, err := manager.Verify(tokenStr, jwtmanager.TokenAccess)
// info.UserID, info.Role
```

Второй аргумент — ожидаемый тип. Токен с несовпадающим `typ` отклоняется явно, а не только по совпадению остальных полей — так дыра из предыдущего раздела закрывается на уровне сигнатуры, а не соглашением между вызывающими.

### Ошибки

```go
var (
    ErrNoPrivateKey     = errors.New("private key is not set")
    ErrNoPublicKey      = errors.New("public key is not set")
    ErrTokenExpired     = errors.New("token expired")
    ErrInvalidSignature = errors.New("invalid token signature")
    ErrWrongTokenType   = errors.New("wrong token type")
    ErrInvalidToken     = errors.New("invalid token")
)
```

`Verify` разворачивает ошибки библиотеки `golang-jwt` в этот словарь, а не пробрасывает их наружу как есть — так смена библиотеки внутри `jwtmanager` не потребует переписывать `errors.Is`-проверки в сервисах. Различайте их через `errors.Is`, например чтобы отличить обычное истечение сессии от подделанной подписи в логах.
